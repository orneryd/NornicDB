## Bug Description
Duplicated code paths were compared pairwise across the NornicDB source: two functions that implement the same operation, on different routes. Each difference below was confirmed by an independent read of the code at 38eb1b91. None of them is reproduced as a user-visible bug; those that are have their own issues (the `IN`/`NOT IN` evaluators, `SET` after `CREATE` vs `MATCH`, multi-`CREATE` executors, `SKIP`/`LIMIT`, integer ordering, string escapes, list literals, index DDL, constraint names, knowledge-policy `ALTER`, index drop procedures) and are not repeated here.

The list is for triage: each item is a place where a fix or feature added to one copy won't reach the other.

## Consequence
**Severity: none confirmed; drift risk.** None of these differences currently has a confirmed user-visible effect. Each is a pair of implementations of the same behaviour that already disagree in edge cases (error class, null handling, validation, cache use, decay filtering). A bug fixed in one copy stays in the other, and a new route that reaches the weaker copy turns the difference into a user-visible bug. Several items (marked "not reproduced") look user-reachable from the code but were not exercised.

None. These are code-level findings; routes are given as `file:line` on 38eb1b91.

Each pair either shares one implementation, or documents why the copies differ.

## Actual Behavior

### Cypher parser / DDL
- **`CREATE CONSTRAINT` header grammar is copied into each `parseCreateConstraint*DDL` function** in `pkg/cypher/schema.go`: ForRequire (used by temporal and domain constraints), NodeKey, SimpleProperty, Type, RelationshipKey/CompositeUnique, Cardinality and Policy. That is at least seven copies of the prefix / name / `IF NOT EXISTS` / `FOR` / `REQUIRE` / `OPTIONS` scan. The copies differ:
  - The legacy `ON … ASSERT` form is accepted by NodeKey, SimpleProperty and Type. ForRequire, RelationshipKey, Cardinality and Policy accept only `FOR … REQUIRE`.
  - NodeKey, SimpleProperty and Type take the `FOR` branch only if `FOR` appears before any `ON`; ForRequire, Cardinality and Policy search for `FOR` regardless of `ON`. The two groups can disagree on a statement with an `ON` token before `FOR`.
  - `FOR` pattern errors: ForRequire, SimpleProperty and Type return the raw `parseCreateIndexForPattern` error. NodeKey maps it to `InvalidPattern('NODE KEY')`, RelationshipKey to `'relationship FOR'`, Cardinality to `'cardinality FOR'`, Policy to `'policy FOR'`.
  - Accepted patterns: NodeKey rejects relationship patterns and RelationshipKey requires one. Cardinality requires an arrow (`parseRelationshipForDirection`), while RelationshipKey ignores direction, so an undirected pattern is accepted only by RelationshipKey.
  - With neither `FOR` nor `ON`, ForRequire and RelationshipKey return `MissingKeyword('FOR')`, while NodeKey, SimpleProperty and Type return `UnsupportedCreateConstraintShape`. `executeCreateConstraint` mostly discards these errors; among the SimpleProperty/Cardinality pair, only Cardinality's pattern error can reach the user.
  - Type's `FOR` branch is a verbatim copy of `parseCreateConstraintForRequireDDL` rather than a call to it.
  - Policy validates the `REQUIRE` expression (`parsePolicyModeRequireExpr`); ForRequire returns it unvalidated.
  - Cardinality re-parses the `MAX COUNT` tail in its error path to produce `PositiveMaxCountRequired`, duplicating `parseCardinalityRequireExpr`.
- **Relationship key / uniqueness in a constraint contract vs the standalone statement** (`schema_contracts.go:186, 306` vs `schema.go:415, 1939`): the standalone statement recognises composite `(r.a, r.b) IS UNIQUE`, unparenthesised `r.a IS RELATIONSHIP KEY` and `(r.a) IS UNIQUE`. Inside a `REQUIRE { … }` contract block these fall through to boolean relationship-expression entries instead of compiled key/unique constraints.
- **`CREATE FULLTEXT INDEX` vs `CREATE [RANGE|VECTOR] INDEX` header** (`parseCreateFulltextIndexDDL` vs `parseCreateIndexDDL`, `schema.go`; `ON EACH` has its own issue):
  - fulltext requires an index name, while the other parsers allow it empty and the callers generate one;
  - only fulltext accepts an unparenthesised `n:Label` and `R1|R2` relationship types;
  - fulltext checks that the tail starts with `OPTIONS` and then discards it (not reproduced: fulltext `OPTIONS` would be ignored), while `parseCreateIndexDDL` returns it;
  - the error for a missing property list differs (`IndexPropertiesRequired` vs `FulltextPropertiesRequired`).
- **`ALTER PROMOTION PROFILE … SET OPTIONS` vs `CREATE PROMOTION PROFILE … OPTIONS`** (`knowledgepolicy_ddl.go` → `storage/schema_knowledgepolicy.go`, `applyPromotionProfileUpdates` around line 624). Not reproduced:
  - `CREATE` matches option keys case-insensitively, while `ALTER` passes the raw key and storage matches exact camelCase, so `scorefloor` is an unknown option;
  - `scope` is accepted by `CREATE` and is an unknown option on `ALTER`;
  - `ALTER` parses literal `0`/`1` as booleans, which the float conversion rejects, so the update is skipped and success reported;
  - wrong-typed values are rejected by `CREATE` and ignored with success by `ALTER`.
  
  Range validation runs on both.
- **`CREATE PROMOTION POLICY` treats `FOR` as optional** (`parseCreatePromotionPolicy`, `knowledgepolicy_ddl.go:951`), so `CREATE PROMOTION POLICY p APPLY {…}` is accepted with no target. The decay-profile binding parser is only entered after its caller has consumed `FOR`.
- **The three `DROP` knowledge-policy parsers** (`DROP DECAY PROFILE`, `DROP PROMOTION PROFILE`, `DROP PROMOTION POLICY`; `knowledgepolicy_ddl.go:300, 306, 309`) are copies that differ only in the error message for a missing name.
- **CREATE-target vs SET-target semantic validation** (`semantic_validation.go:93, 102`): the CREATE validator detects its clause with `findKeywordIndexInContext` and skips schema/administration `CREATE` commands; the SET validator detects `SET` with `containsKeywordOutsideStrings`.
- **Static vs runtime `labels()`/`type()` argument checks** (`match_semantic_validation.go:134` / `semantic_validation.go:83` vs `row_graph_function_validation.go:107`):
  - the static check also covers `properties()` and `length()`;
  - it rejects only known incompatible binding kinds, while the runtime check rejects any evaluated value that isn't a node/relationship;
  - in a list comprehension the static check never binds the comprehension variable;
  - the static check runs only for `RETURN`, while the runtime check runs for `WITH` and `RETURN`, only on the row-pipeline route and only when rows exist.
- **Comma splitters** (`splitTopLevelComma`, `call_shared_utils.go:12`; `splitTopLevelCommaKeepEmpty`, `set_merge_strict.go:69`; the property-map splitter in `pattern_parser.go:157`; the `SET` splitter in `set_helpers.go:80`):
  - the map and `SET` splitters let the nesting counter go negative on an unbalanced closer, while `splitTopLevelComma` floors it at 0;
  - the map and `SET` splitters drop empty middle segments, while `splitTopLevelComma` keeps them;
  - none of them treats backticks as quoting.
- **List-literal parsers** (`parseBindingLiteralList` for compiled `WHERE` and CALL-tail `WHERE`, `binding_where_compile.go:495` / `call.go:2042`, vs `parseLiteralListForPipeline`, `pipeline_executor.go:3692`):
  - quoted strings: the first strips the outer quotes without an escape check or decoding, while the second requires one whole quoted string and decodes escapes;
  - floats: the first accepts `inf`/`infinity`/`nan` and keeps `-0.0`, while the second requires `.`/`e`/`E` and turns zero into `+0`;
  - nested lists/maps: the second parses them, while the first rejects the whole list.

### Storage reads (and the related storage write / validation paths)
- **Label scans.** Four implementations differ:
  - `BadgerEngine.GetNodesByLabel`;
  - `BadgerEngine.GetFirstNodeByLabel`;
  - engine `StreamNodesByLabelProjected`, used by the Cypher label-scan fast paths (`pipeline_executor.go:670`, `match_multi.go:1314`, `executor_match_vector_cosine_fastpath.go:463`);
  - `BadgerTransaction.StreamNodesByLabelProjected`, which reads from a pinned snapshot (`snapshotTx`) or from MVCC at `readTS` (`badger_transaction.go:1638-1645`).

  The differences:
  - Only the transaction streams re-check the decoded node's labels. The engine readers trust the label index, so a stale index entry is emitted by them and filtered by the transaction streams.
  - The transaction streams return non-NotFound `Get` errors and decode errors; the engine readers skip them silently.
  - Caches: the engine stream reads the unversioned `nodeCache` and never fills it. `GetNodesByLabel` reads and back-fills it. `GetFirstNodeByLabel` uses no cache. The pinned-snapshot stream uses the version-checked node-body cache. With a stale `nodeCache`, these can return different bodies for the same node.
  - On a cache hit with no projection, the pinned-snapshot stream reloads embeddings (`loadNodeEmbeddings`), while the engine stream returns `copyNode(cached)`.
  - The engine stream checks `ensureOpen` and records scan metrics; the pinned-snapshot stream does neither.
  - Decay: the engine readers and the pinned-snapshot stream skip index-tombstoned entries (when decay is enabled and not revealed); the MVCC `readTS` stream has no tombstone check. The engine and pinned-snapshot streams run `filterNodeByDecay` on the projected node, while the MVCC stream scores the full node and then projects. Promotion rules read entity properties, so the results can differ.
  - The MVCC stream resolves the visible version through the head/record chain and registers an MVCC snapshot read; the pinned-snapshot stream reads the current node key with no head lookup.
- **`GetEdgeBetween` typed head pointer vs edge-between set index** (`badger_queries.go:954` vs `:929, 965`):
  - a load failure on the head path returns a wrapped error (logged as Warn before the fallback), while the set path skips the entry;
  - the head path checks both the head-key and the set-index tombstone, while the set path checks only the set-index key.
- **Temporal lookups** (`NamespacedEngine.GetTemporalNodeAsOf`, `namespaced.go:766`, used by `call_temporal.go:135`, vs `IsCurrentTemporalNode`, used by `match_multi.go:1249/1291/1342`):
  - when the index path finds nothing, only `IsCurrentTemporalNode` falls back to a label scan;
  - the index path loads raw bodies without decay filtering, while that fallback applies it;
  - `GetTemporalNodeAsOf` requires exactly one matching constraint, while `IsCurrentTemporalNode` requires the node to be current under every temporal constraint on its labels.
- **Transaction point reads, node vs edge** (`BadgerTransaction.GetNode` / `GetEdge` committed readers):
  - with no MVCC head, a node falls back to a primary-key read, while an edge returns `ErrNotFound`;
  - with `readTS` zero, a node is read through the pinned snapshot reader, while an edge is read through the writer transaction.
- **`StreamNodeChunks` in `AsyncEngine` vs `WALEngine`**. No non-test production caller was found outside the engine decorators.
  - The WAL layer delegates to `BadgerEngine.StreamNodeChunks`, which doesn't filter decay-suppressed nodes; the Async path goes through `StreamNodes`, which does.
  - A `chunkSize <= 0` is not defaulted on the Async path or the WAL fallback (a negative value panics in `make`), and is defaulted to 1000 on the delegated path.
  - `ErrIterationStopped` is re-delivered to the callback on the Async and fallback paths.
  - Only the Async path checks context cancellation.
- **Decay visibility, node vs edge** (`filterNodeByDecay` vs `filterEdgeByDecay`): nodes pass `UpdatedAt` as the version anchor, while edges pass `CreatedAt`, so with `ScoreFromVersion` edge decay never re-anchors on update. This matches the Cypher-side edge scoring.
- **Constraint contracts: validation at contract creation vs at commit** (`storage/constraint_contracts.go:305` → `:334-355` vs `BadgerTransaction.validateConstraintContracts`, `:1266, 1292`):
  - a missing or decay-hidden endpoint or pattern neighbour makes the creation-time check fail with the raw `GetNode` error, while the commit-time check skips the edge or reports `StorageSchemaMissingRelationshipEndpoint`. The same dangling neighbour can fail contract creation and be ignored at commit;
  - edges come from the engine adjacency in one and from the transaction overlay in the other.
- **Relationship creation in a transaction, bulk vs single** (`transaction_storage_wrapper.go:431/441` vs `:151/157`):
  - a nil edge gives `ErrInvalidData` in the bulk path and `ErrInvalidID` in the single path;
  - an empty bulk input returns before the lifecycle check;
  - a failure part-way through a batch leaves the earlier edges buffered.
- **`BadgerEngine.UpdateNode` insert branch vs `CreateNode`** (`wal_engine.go:585/606`, `async_engine.go:647 → 755/770` vs `wal_engine.go:571`). When the node key is absent, the upsert branch:
  - doesn't default `CreatedAt`/`UpdatedAt`;
  - doesn't write the index-entry catalog;
  - doesn't apply temporal indexes;
  - returns raw Badger errors instead of localized ones.
- **`UpdateNode` vs `UpdateNodeEmbedding`** (embed worker, `embed_queue.go`):
  - the embedding write doesn't take the `beginWrite` close barrier and records no metrics;
  - the pending-embed index is only deleted when new embeddings are non-empty, and never re-added when they are cleared;
  - the cache is updated with `cacheOnNodeUpdated` instead of `cacheOnNodeUpdatedWithOldNode`.
- **MVCC bootstrap, node vs edge page collectors** (`badger_mvcc.go:1795` vs `:1880`): the node collector decodes bodies with embeddings (extra chunk reads) although bootstrap uses only timestamps. This affects cost only.
- **WAL recovery visitors**: `VisitEdge` flushes buffered nodes before buffering an edge; `VisitNode` doesn't flush buffered edges.
