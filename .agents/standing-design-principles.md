# Standing design principles
These principles apply while choosing a solution, writing code, and correcting code.

1. If the required result, scope, priority, acceptable behavior, consequence, or other operator-owned meaning is ambiguous, ask and repeat until it is clear. Never guess or infer operator-owned meaning. Once it is clear, ordinary technical decisions remain agent-owned.
2. Preserve the exact approved scope. Do not add unapproved hardening, improvements, safeguards, cleanup, refactors, features, or changes to adjacent systems. Technical discovery and architectural preference create no scope. If work outside the approved scope appears necessary, ask before changing it.
3. Fix root causes only. Shims, workarounds, bypasses, symptom suppression, masking, and fragile partial solutions are prohibited. Cost, time, convenience, and implementation difficulty do not justify them. If the root cause cannot be fixed within the approved scope, ask instead of substituting a workaround.
4. Build only the exact product result required by current specs and operator decisions. Do not silently strengthen that result or turn an acceptable variation into a defect.
5. Do not independently design or implement edge cases. Code beyond the exact required behavior is justified only for a failure reasonably likely during ordinary operation that has a meaningful product consequence.
6. A technically possible scenario remains an edge case when it depends on narrow timing, exceptional circumstances, unsupported state, unusual actions, several independent events aligning, or another condition not reasonably expected in normal operation. Proving that it can happen does not justify engineering for it.
7. A product consequence means that the requested customer, business, data, money, access, or service result becomes materially wrong, missing, unsafe, or unusable for a real affected population. Internal neatness, temporary technical state, process records, theoretical consistency, reviewer concern, and differences with no meaningful effect on the requested result are not product consequences.
8. Distinguish an established defect in required behavior from an unapproved precaution. Establish the approved product result, affected population, ordinary-operation likelihood, and meaningful product consequence before adding behavior. A merely reproducible exceptional scenario does not by itself authorize engineering for it. Uncertainty does not authorize precautionary code.
9. Among complete root-cause solutions, choose the simplest design that satisfies the exact required result. Never reduce cost or effort by weakening the result or introducing a workaround.
10. Partial success is failure. Completion requires every requested part.
11. Nothing required disappears silently. Complete it, route it truthfully, or return missing meaning to the operator.
12. Lead verification with the requested product outcome, its supported conclusion, evidence, and practical limits. Prove the complete affected correction, not just its last failing example. Do not claim broad correctness from statement coverage, static candidates, or a narrower input population.
13. When completeness matters, establish the population with a repeatable extractor, query, parser, capture, or comparator; assess every member and add semantic members the extraction cannot find. The agent owns complete coverage and supported conclusions.
14. Keep each behavior in one canonical owner and implementation. Extend that owner instead of duplicating the same behavior, decision, state, state transition, workflow, alternate path, or implementation. Converge existing in-scope divergence encountered during the approved change into that canonical implementation. If genuinely new behavior has no owner, create exactly one. Separate components are valid only when they own genuinely different responsibilities. This principle applies only to the approved change and does not authorize unrelated consolidation or refactoring.
15. Component maintenance boundary: Distinguish components we maintain from components maintained by others. Implement changes through our components and supported integration, configuration or extension mechanisms. Patching externally maintained code is prohibited unless unavoidable for the required result; convenience is not necessity. Before any such patch, establish why those mechanisms cannot deliver the result and request explicit permission under THIRD-PARTY COMPONENT PATCH, naming the component and exact code change. Clearly explain that updates can overwrite the patch and upgrades or other components can break, identify other affected behavior, and explain the continuing maintenance burden. Proceed only with the operator's explicit approval for that patch. Supported configuration is not code patching and remains subject to ordinary scope and permission rules.
16. Every state field has one writer.
17. Handle likely failures outside our control. Do not add recovery, fallback, or masking for hypothetical defects in our own code or failures of our own infrastructure. Let owned failures remain visible. Every implemented failure path persists the failed operation, provider or request ID when available, error code, and outcome; then fix owned causes.
18. A required product effect in normal supported operation must not depend only on one event being noticed once. Reuse a suitable periodic process to catch misses. Repetition must be safe, while money and access effects occur exactly once.
19. One-time data migration or repair is an operation, not permanent product behavior. Permanent migration code is prohibited. Never add permanent product code that targets a fixed known population or exists only to handle its old state. A generic supported command remains generic when the operator supplies an ID.
20. These principles do not authorize unrelated state, jobs, logging systems, refactors, hardening, features, or cleanup.
