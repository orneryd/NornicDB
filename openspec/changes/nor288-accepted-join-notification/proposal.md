# NOR-288: retire accepted join work before settlement observers

Status: partial correction under verification; NOR-288 remains open.

The exact retained WAL reproduction shows a caller's settlement callback closing its WAL engine while the same accepted join is still enrolled in work that Close joins. The same join/notification unit serves Standalone and asynchronously launched native/Raft applied settlement. Release the caller's own join enrollment before delivering terminal notification or registering an immediately delivering native observer. Native outcome composition and pending bookkeeping remain before release. Pending stays pending with no settlement callback; applied commands and acknowledgement errors keep their actual outcome and committed image.

Each release guard is local to its single join goroutine. Delivery and deferred cleanup invoke it synchronously; late OnSettled closures retain the receipt, not this guard. A local idempotence flag replaces sync.OnceFunc after an overlay experiment restored the measured baseline allocation count (341 vs343 allocations per bounded WAL commit). No global lifecycle primitive, notification queue or new goroutine was introduced by the applied-join correction. Short ordered benchmark latency samples are not a speedup claim.

The released `AcceptedEntityCommitHandle.JoinContext(ctx, outer, transportErr)` keeps its exact three-argument signature and behaviour; the release-aware entry is the separately named `JoinContextWithRelease(ctx, outer, transportErr, release)`, which both in-tree transports needing lifecycle release (the WAL accepted-entity commit and the replication accepted-by-apply submitter) now call. Both entrypoints converge on the same private record/join owner, so there is one join protocol and the released Go API keeps its shape; `pkg/storage` holds a compile-time assertion of that exact three-argument method for out-of-package callers. No HTTP/Bolt contract changes are claimed.

## Definite Raft discard (corrected)

Two direct-Go Raft discard observers deterministically self-waited in Shutdown: uncommitted-log truncation and retirement queue drain. Both returned the right CommitDiscarded outcome before blocking, on macOS and Linux, with a passing non-reentrant control. The causal owner has two parts, not the discard notification alone: the definite rejection delivered the caller's settlement observer inside the deciding frame, which is an admitted Raft unit or the retirement dispose hook that Shutdown joins; and the accepted command's commit waiter was bounded by the delivered receipt (Done), so it also waited for that same observer.

The correction splits native decision from foreign delivery at their one owner, CommitReceiptOwner. `claim` validates and records the outcome, publishes the physical decision, detaches the settlement callback and signals the state change under the receipt mutex, synchronously with the deciding frame. Only the foreign settlement callback and the Done close it gates follow, in `deliverTerminal`: synchronously for an ordinary `Resolve`, whose callback-before-Done order is unchanged. A definite rejection records through the same `claim` and starts that same delivery in a frame of the receipt's own, from the deciding frame itself. There is one resolution protocol and one `Resolve` entry; only the frame that runs the foreign delivery differs, at the one call site that decides inside joined transport work.

No new terminal channel was added. The receipt's existing state-change channel already owned these transitions: it rotates on a recovery-pending observation and on `beginRecovery`, and it now closes when the terminal outcome is recorded, before the observer runs. `CommitReceipt.Decision` returns the recorded outcome with that channel under the mutex, and Raft's accepted commit waiter now snapshots that pair, rearms while the outcome is recovery-pending, and leaves on the recorded terminal decision. The waiter still honours the unchanged commit timeout and the shutdown signal, a pending observation never becomes terminal and never restarts the timeout, and pending error bookkeeping still reports through `ObservePending`. `WaitOutcome` already joins Done after it sees a terminal state, so external waiter completion still follows the observer.

AcceptedEntityCommitHandle.Reject retires the command's native frame and accepted authority in the deciding frame and hands only the terminal notification to that detached delivery, so a transport whose Shutdown joins the deciding frame also joins the native cleanup. The definite branch never consults engine admission, so a rejection is still never reported as recovery-pending. This stage adds no queue, global scheduling protocol, polling, untracked native cleanup or early release of active native work; the two reproductions now run by default.

## Remaining ticket scope

Registry retention: `registerAcceptedEntityApplication` reads the application pointer under the engine mutex, unlocks, and only then aborts the duplicate frame and registers its settle. A retained pointer is not invalidated by later registry removal, and the ordering control that observes registry-absent delivery does not address that. The owner-level interleaving is now established rather than assumed: after retirement the retained pointer still names the same application, its `OnSettled` cannot deliver before the accepted owner's own observer returns because the receipt's Done gates it, and it then delivers that one recorded terminal outcome exactly once, without fabricating or duplicating an outcome. The production interleaving itself (registry read, unlock, retirement, OnSettled) is not reproduced: that needs a pause inside `registerAcceptedEntityApplication` that the package does not expose. The consequence of using such a pointer is established; the concurrent interleaving remains unverified, so no new defect and no no-repro claim is made.

The canonical staged duplicate checker runs over the staged worktree scope; it does not require an indexed immutable commit or reingestion. The earlier statement that this stage could not run it is corrected: the parent ran the same 24-function checker over this proposal while it was uncommitted at the matching e8 base.
